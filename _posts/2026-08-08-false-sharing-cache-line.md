伪共享（false sharing）：现代多核 CPU 上，多个线程运行在**不同物理核心**，各自读写不同的变量，但这些变量位于同一条 **cache line**（缓存行）内，写入时互相触发整行失效与重取——**缓存一致性以 cache line 为粒度工作**，故无关的写操作也会互相拖累。它不构成数据竞争，**程序逻辑正确，但性能严重受损**。本文按定义、硬件机制、典型场景、检测方法与修复手段展开。

## 伪共享的定义与定性

伪共享的核心特征可以归纳为两条：

- **线程间不共享任何变量**：每个线程只读写自己的字段，字段之间没有真实的逻辑依赖，不存在数据竞争。
- **但共享同一条 cache line**：字段在内存中的物理位置相邻，落在同一 cache line 的 64 字节（x86-64 通常值）范围内。

因此伪共享在正确性层面完全无害，却在性能层面造成与真实共享相当的通信开销。区分这一点很重要：排查性能问题时，伪共享与数据竞争是两类不同的问题，检测与修复手段也不同。

## 硬件机制：cache line 粒度的缓存一致性

伪共享成立的前提是**现代主流多核 CPU（x86-64、ARM 等）通过硬件缓存一致性协议维护核间共享**。cache line（x86-64 上通常为 64 字节）是缓存的**分配、失效与核间传输的统一粒度**——一致性协议（如 MESI）维护各核心副本一致性的最小单位就是 cache line，而不是单个字节；各核心持有的同行动副本通过失效与重取保持同步，这是多线程共享内存编程能够成立的基础。在此前提下，多线程并发编程中**只要多个线程高频写各自的相邻字段，就会遇到伪共享**，无需其他特殊条件。一致性域之外的内存（如 DMA 缓冲、设备内存）不做缓存一致性处理，属于另一类问题，不在本文范围。

### 缓存层次与访问模型：私有缓存、共享末级缓存与逐级查找

现代 x86-64 处理器的缓存是分层结构，各层的归属与典型规模如下：

| 层次 | 归属 | 典型容量 | 典型访问延迟 |
|------|------|---------|-------------|
| L1（i/d 分离） | 每核心私有 | 32–64 KB | 约 4 周期 |
| L2 | 每核心私有 | 1–2 MB | 约 10–14 周期 |
| L3（LLC） | 同 socket 内共享 | 8–64 MB | 约 40–60 周期 |
| 主内存 | — | — | 约 100 周期 |

缓存查询是**逐级进行的**：程序绝大部分内存访问 cache hit 于 L1；cache miss 则向下一级发起查询（L2 → L3 → 主内存），直到某一级 cache hit 或到达主内存。数据取回后**以整条 cache line 为单位**依次填充 L3 → L2 → L1，此后同一 cache line 的访问均 cache hit 于 L1。整个逐级查询与填充由硬件完成，对软件透明。两个推论：

- **加载粒度是 cache line 而非字节**：一次 cache miss 取回整行 64 字节，同一行内的后续访问全部 cache hit（空间局部性）；相邻数据的首次访问也因此免于各自 miss。
- **失效等价于强制 cache miss**：cache line 副本被一致性协议失效后，该核下一次访问该行必然 L1/L2 cache miss，需逐级重取——伪共享正是让每次写入都触发一次这样的强制 cache miss。

同一 cache line 会在多个核心的 L1/L2 中各持有一份副本。伪共享的失效正是发生在这些**私有副本**之间。

### ⭐ 发生条件：不同物理核心上的线程

伪共享的代价来自私有缓存副本之间的跨核失效，因此其发生条件有精确的界定：

- **必须运行在不同物理核心上**：同一物理核心（包括超线程/ SMT 下共享 L1/L2 的两个逻辑线程）上的多个线程读写同一 cache line 只有一份副本，不存在跨核失效与 RFO，不会遇到伪共享。
- **低延迟系统是典型高发环境**：行情系统通常将工作线程绑定（pin）到不同物理核心以换取真并行，跨核失效由此必然发生。

### 写失效与 RFO

一次伪共享写操作在硬件层面经历的完整路径：

1. 核心 A 写入某字段所在 cache line，一致性协议向所有持有该行副本的核心广播失效消息（invalidation）；
2. 核心 B 持有的同行动副本随之失效——等价于强制 cache miss；
3. 核心 B 下一次访问同一行时发生 cache miss，触发 RFO（Read For Ownership）——从其他核心或内存重新获取该行的最新数据。

一次完整的写失效 + 重取路径的典型代价在数百周期量级：脏行写回、跨核传输、重新加载依次发生。注意该代价是**每次写入**都会支付，而非仅首次。对核心 B 而言，伪共享的净效果是**每次写入自己的字段，都把自己的 cache line 访问从"L1 cache hit"变成"跨核重取"**。

#### 代价的量化与拓扑影响

重取时数据可能来自 L3，也可能直接来自对端核心缓存（cache-to-cache 转发）。代价随线程所在拓扑位置变化：

| 场景 | 失效后重取来源 | 典型代价 |
|------|---------------|---------|
| 同 socket 伪共享 | 共享 L3 或对端核心缓存 | 数十周期 |
| 跨 socket 伪共享 | 对端核心缓存（经互连） | 数百周期 |

多路服务器上，不同 socket 的核心通过互连（Intel UPI / AMD Infinity Fabric）处于同一系统级一致性域，数据可**直接从远端核心缓存传输，不必经过主存**；但失效与重取经过互连往返，代价显著高于同 socket，且乒乓效应下每次传输都占用互连带宽。因此多路部署应避免让共享热点数据的线程分布在不同的 socket——线程绑定时需同时考虑核心亲和性与 NUMA 拓扑，把互有数据依赖的线程绑定到同一 socket。

### 乒乓效应

当两个核心分别反复写入自己那一半 cache line 时，该行在两个核心之间来回传输，形成 cache line 乒乓（ping-pong）。每次传输都包含完整的失效与 RFO 流程，吞吐被核间通信速率限制。

乒乓与真共享（真正读写同一个变量）的对比：真共享的每一次传输至少携带了必要的通信数据；伪共享的每一次传输都是纯粹的浪费——被传输的字节中没有任何一方需要对方写过的内容。

## ⭐ 典型场景

### 示例：相邻的原子计数器

```cpp
struct Stats {
    std::atomic<uint64_t> buy_count{0};   // 线程 A 只更新这个
    std::atomic<uint64_t> sell_count{0};  // 线程 B 只更新这个
};  // 两个字段落在同一条 cache line
```

线程 A 每次写 `buy_count` 都会使线程 B 持有的整行副本失效，线程 B 下一次写 `sell_count` 便触发一次 RFO。两个字段之间没有任何真实依赖，写操作却相互拖累。实测中，双线程各自写不同字段的吞吐可能**低于串行执行**；伪共享的代价可以高到与竞争同一把锁相当，乃至更差——锁竞争至少是"必要的同步"，伪共享则是无谓的同步。

### 低延迟系统中最常出现的位置

- **无锁队列的头尾指针**：producer 写 `head`、consumer 写 `tail`，两个指针若放在同一结构体中，即构成经典伪共享——这与无锁队列的设计初衷（消除锁竞争）直接矛盾。
- **每线程计数器数组**：`per_thread_stats[tid]` 的元素按线程号顺序排布，相邻两个元素（尤其元素小于 64 字节时）共享 cache line，线程 0 与线程 1 的写入互相使失效。
- **结构体数组（AoS）布局**：同一结构体的不同字段被不同线程更新，而数组中每个元素恰好跨越若干 cache line，相邻元素的对应字段共享同一行。
- **含热点字段的结构体**：lock、sequence number、seq 等被多个线程频繁更新的字段集中在一个结构体中。

上述场景的共同点：字段之间无依赖，但被不同线程高频写入。伪共享的伤害与写入频率成正比——写入越频繁，失效与 RFO 越密集。

## ⭐ 检测方法

伪共享无法通过正确性检查发现，需要针对性的工具或实验：

- **perf c2c**：分析 cache-to-cache 传输，直接定位发生伪共享的 cache line 与代码位置。该工具以"哪些行在核间高频传输"为线索，是定位伪共享的最直接手段。
- **perf stat -e cache-misses**：观察整体 cache miss 率是否异常偏高，作为粗筛。
- **VTune Access Contention 分析**：基于硬件采样标记存在访问竞争的行，适合大规模分析。
- **Padding 实验法**：最朴素的诊断——给可疑字段加 padding 后性能出现显著变化，即确认伪共享存在。该方法成本低，常用于验证性确认。

## ⭐ 修复手段

修复的核心原则：**让不同线程读写的变量落在不同 cache line**。三种典型手段：

- **对齐与填充**：使用 `alignas(64)` 对齐结构体，或在字段之间手动填充字节，使不同线程的字段落在不同 cache line。
- **标准手段**：C++17 提供 `std::hardware_destructive_interference_size`，表示当前平台的 cache line 大小（通常为 64，部分平台为 128），可作为 padding 尺寸的标准来源，避免硬编码 64。
- **布局拆分**：将热点字段拆到独立 cache line、独立分配，或将每线程数据结构改为数组结构体（SoA）布局，让不同线程访问的字段天然分离。

三种手段的代码示意：

```cpp
#include <atomic>
#include <new>   // std::hardware_destructive_interference_size

// ① 对齐与填充：用 alignas 让整个结构体按 cache line 对齐，
//    相邻实例落在不同 cache line，互不干扰
struct alignas(64) Counter {
    std::atomic<uint64_t> val;
};

// ② 标准手段：以平台 cache line 大小为 padding 单位，不硬编码 64
struct PaddedCounter {
    std::atomic<uint64_t> val;
    alignas(std::hardware_destructive_interference_size) char pad;  // pad 纯占位，从不读写
};

// ③ 布局拆分：头尾指针拆分到独立 cache line（无锁队列场景）
struct alignas(64) SPSCQueue {
    alignas(64) std::atomic<size_t> head;  // producer 只写 head
    alignas(64) std::atomic<size_t> tail;  // consumer 只写 tail
};
```

### 那么代价是什么呢

padding 并非免费：`alignas(64)` 使每个对象从几字节膨胀到 64 字节，会增加缓存的使用量，可能造成其他代码 cache miss 率上升。因此修复前需确认两点：

- **区分伪共享与真共享**：若两个线程确实在读写同一个字段（真共享），padding 无法消除通信，反而掩盖问题，此时需要的是同步原语而非填充。
- **评估对象规模**：大量小型对象的场景（计数器数组、消息池）padding 代价显著，优先考虑布局拆分而非逐对象填充。

### 修复的验证

修复后应回到检测手段确认生效：重跑 perf c2c 观察目标 cache line 的核间传输是否消失，或用吞吐/延迟对比验证。单测无法覆盖此类性能修复，验证必须落在真实部署环境与真实负载上。

---

> **小结**：伪共享是"不共享变量、却共享 cache line"引发的性能问题——缓存一致性以行粒度工作，无依赖的写操作也会相互失效。典型场景为无锁队列头尾指针、每线程计数器数组与 AoS 布局中的相邻热点字段。检测依赖专用工具（perf c2c、VTune）或 padding 实验；修复以对齐、padding 与布局拆分为主，核心原则是让不同线程读写的变量落在不同 cache line。
