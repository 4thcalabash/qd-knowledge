"虚函数慢"是常见的经验性判断，但真实开销需要精确分解：虚调用本身的指令代价只有几个周期，量级级的损失来自失去内联、分支预测失败与缓存未命中。加速的本质是去虚化（devirtualization）——让编译器在编译期或通过守卫分支重新确定调用目标。本文按开销来源与消除手段两个维度展开，聚焦实现原理与使用规范。

## 虚函数调用的开销来源

### 指令层面：两次依赖加载

一次直接调用在 x86-64 上是一条指令，目标地址编译期已知：

```asm
call <直接地址>
```

一次虚调用则包含三步：从对象加载 vptr，从 vtable 中加载函数指针，再间接调用：

```asm
mov rax, [rdi]          ; ① 加载 vptr（单继承下通常位于对象偏移 0）
mov rax, [rax + off]    ; ② 从 vtable 加载函数指针（slot 偏移编译期已知）
call rax                ; ③ 间接调用
```

![虚函数调用链]({{ site.baseurl }}/assets/images/virtual-call-chain.svg)

相比直接调用，虚调用多出两次处于关键路径上的依赖加载（取 vptr、取函数指针），单纯这几条指令的代价只有几个周期，可以忽略。

### ⭐ 失去内联：最实质的损失

间接调用使编译器无法内联（内联要求目标在编译期已知），连带损失一串优化机会，这是虚调用最致命的成本：

- **跨对象优化失效**：表达式 `obj.get().x + 1` 在 `get()` 内联后可直接对字段做常量传播与冗余消除；虚调用下返回值不可跨调用分析。
- **临时对象消除失效**：内联后拷贝/移动构造可被省略（copy elision），虚调用下无法执行。
- **调用约定开销**：参数与返回值按 ABI 在寄存器与栈间传递，本可跨调用保持的值（如循环变量）被保存与恢复，循环内调用虚函数时该开销累积。
- **无法按具体类型特化**：只访问单个字段的派生类虚函数，内联后是一条 load；虚调用则是完整的过程调用。

量化直觉：**getter 类虚函数（只返回一个成员）的虚调用开销比内联版本高出一个数量级**——内联版本就是一条 load，虚调用版本则要经历完整的调用过程。

### 分支预测：单态与多态调用点

现代 CPU 用间接分支预测器（基于 BTB 与目标历史，如 TAGE 类机制）记录每个调用点的历史目标：

- **单态调用点**（monomorphic）：调用点总是命中同一个具体类型，预测准确率接近 100%，间接调用的预测成本趋近于零——这是很多虚函数实际运行并不慢的原因。
- **多态调用点**（polymorphic）：同一调用点交替命中多个类型，预测器只能猜测一个目标，猜错时流水线需冲刷重取，惩罚约 15~25 个周期（取决于流水线深度）。

虚调用变慢的典型场景是：**一个循环里交替处理不同类型对象**——每个调用点的目标持续变化，预测持续失败，叠加非内联损失，性能可差出数倍。

### 缓存行为：vtable 与 icache

- 每个多态类一张 vtable。调用点在多个类型间切换时，每次加载不同类的 vtable，这些 vtable 分散在不同 cacheline 上；访问频繁而 vtable 不在 cache 中时，每次都是数十周期的 cache miss。
- 间接调用的目标无法被硬件预取器提前发现，不同热虚函数的代码块在 icache 中互相驱逐；内联版本则是连续代码，预取友好。

### 对象布局：vptr 空间

每个多态对象多一个 vptr（x86-64 上 8 字节），多继承下可能多个。对小型对象批量容器（如 `std::vector<SmallPoly>`）影响显著：对象变大，缓存容纳量下降、分配开销上升。若只存储指针（`std::vector<Base*>`），vptr 不占额外空间，但失去内联与预测的代价依然存在。

### 开销排序

| 排序 | 开销来源 | 量级 / 场景 |
|:----:|----------|-------------|
| 1 | 失去内联 | 数量级影响，getter 场景一条 load vs 完整调用 |
| 2 | 分支预测失败 | 目标多变的调用点，约 15~25 周期/次 |
| 3 | 缓存 | vtable cache miss 数十周期，icache 驱逐 |
| 4 | 指令与 ABI | 两次依赖加载、寄存器压力，几个周期 |
| 5 | 对象布局 | vptr 每对象 8 字节 |

## 去虚化：消除开销的手段

去虚化按"编译器能确定具体类型"的程度分为四个层次。

### 静态去虚化

核心思想：**间接调用的前提是编译器不知道动态类型；只要它知道了，就能改写为直接调用并内联**。

无需代码改动的场景——编译器已看到完整类型：

```cpp
Derived d;
d.virtual_fn();             // 类型完全已知，直接调用

Base* p = new Derived();
p->virtual_fn();            // 编译器看到 new Derived() 的完整类型
                            // -O2 下 GCC/Clang 均可去虚化
```

GCC/Clang 的 `-fdevirtualize` 在 `-O2` 默认开启，执行的正是这类转换：若分析出某虚调用点所有可能目标只有一个具体类型，就改写为直接调用。

`final` 关键字给编译器提供更长远的信息：若某个基类的所有对象实际上都是某个 final 派生类（在完整类型可见的前提下），所有虚调用点都可去虚化：

```cpp
struct Base { virtual int f(); };
struct Derived final : Base { int f() override; };

void use(Base* p) { p->f(); }   // 编译器可假设 p 动态类型为 Derived → 去虚化
```

注意 `final` 的作用边界：它只在**编译器能看到完整类层级**时有效。若某个派生类定义在另一个编译单元且未被看到，编译器必须假设存在未知子类，`final` 也无济于事。因此 `final` 的实际价值是优化提示与防意外继承的保证，性能收益通常需配合 LTO 兑现。

### 链接期去虚化

单编译单元去虚化的天花板是"看不到其他编译单元中的派生类"。链接期优化（`-flto`）把整个程序的类层级暴露给编译器：

```bash
g++ -O2 -flto main.cpp base.cpp derived.cpp -o app
```

全程序可见所有派生类后，若某基类只有一个具体实现，所有虚调用点都可去虚化。Clang 的 `-fwhole-program-vtables`（需配 `-flto`）更进一步，按全程序可见性合并 vtable，直接缩减间接跳转的目标集合。代价是编译时间上升、构建流程需整体重组、与部分第三方库不兼容。

### 推测性去虚化

静态去虚化的盲区是：**调用点处理多个类型，但其中一个类型占压倒性比例**（例如 99% 的对象是 `DerivedA`，接口仍允许 `DerivedB`）。静态分析对此无能为力，但可以推测。

**PGO + 间接调用提升（Indirect Call Promotion，ICP）**：

```bash
# 第 1 步：插桩编译并运行典型负载，生成 profile
g++ -O2 -fprofile-generate ... && ./app

# 第 2 步：使用 profile 重新编译
g++ -O2 -fprofile-use ...
```

编译器根据 profile 将热调用点改写为守卫分支：

```cpp
// 原始：p->f();
if (vptr_of(p) == vptr_of(DerivedA))   // 守卫：一条 vptr 加载 + 比较
    DerivedA::f(p);                    // 直接调用 + 内联（热点路径）
else
    p->f();                            // 慢路径，回退虚调用
```

守卫命中的成本是 1 次加载 + 1 次比较 + 1 条条件分支，远小于虚调用本身；分支预测器对"几乎总是命中"的条件预测极准。热点类型被内联，边缘类型仍保持正确语义。

无 PGO 的版本：GCC 的 `-fdevirtualize-speculatively` 默认开启，基于启发式做推测性去虚化，收益不如 PGO 精确。Clang 侧则通常依赖 `-fstrict-vtable-pointers` 或 PGO 触发。

**`-fstrict-vtable-pointers`**：Clang 推测性去虚化选项，假设 vptr 在函数执行期间不变；该假设并非语义保证，vptr 变化场景（如构造期间调用虚函数）下可能产生错误结果。

### ⭐ 设计层面消除 vptr 间接层

前三层是"编译器帮忙消除"，这一层是"设计上不产生虚调用"。

**模板 / CRTP（静态多态）**：类型在编译期绑定，天然可内联、可特化，无 vptr、无间接跳转：

```cpp
template <typename Derived>
struct Processor {
    void run() { static_cast<Derived*>(this)->step(); }  // 编译期绑定
};
```

代价：代码膨胀；类型不可统一存储——`vector<Processor<A>*>` 无法存放 `Processor<B>*`，因为没有公共基类。

**`std::variant` + `std::visit`（封闭类型集）**：

```cpp
using V = std::variant<Circle, Square>;
std::visit([](auto&& s) { s.draw(); }, v);
```

`std::visit` 编译为基于 index 的跳转表/switch：每次调用是 1 次 index 加载 + 1 次条件跳转（分支可预测，且无间接目标预测问题），每个分支内是直接调用并可内联。适用条件是**类型集合封闭且较小**。相比虚调用多了 index 检查开销，但少了 vptr 间接层，且每个分支都能内联，通常整体胜出。

**函数指针表 + 类型标签**：手动版 variant——对象存 `type_id` 与函数指针数组，调用用 switch 分发。表可以连续布局、局部化，缓存行为优于分散的 vtable，适合对缓存敏感的热循环。

### 运行期动态注册：函数指针 + context

插件、动态订阅等场景中，回调提供方在运行期才确定，类型在编译期不可知，模板与 `std::variant` 均不适用。此时回调应保存为函数指针 + context 的形式，每个订阅者一个 handler：

```cpp
struct Handler {                    // 订阅者提供的回调与状态
    void (*fn)(void*, const Quote&);
    void* ctx;
};
```

该形态的要点是**保持调用点单态**：每个 handler 的函数指针是固定目标，间接分支预测器对它的命中率接近 100%；与 `std::function` 相比少一层 SBO 分支判断，且不存在堆分配回退路径。

多个订阅者并存时，使用 `std::vector<Handler>` 存储——元素类型相同，循环内对每个元素的调用仍是同一固定目标，预测器对"固定目标循环遍历"的模式命中率极高。应避免把不同订阅者包装为不同闭包混入同一容器，那会使调用点退化为多态。

```cpp
// 注册（冷路径）：连接建立、订阅时发生一次
void subscribe(void (*fn)(void*, const Quote&), void* ctx);

// 行情到达（热路径）：调用点单态，无堆分配、无 SBO 分支
void on_tick(const Quote& q) {
    for (auto& h : handlers_) h.fn(h.ctx, q);
}
```

关键规范是注册与回调分离：类型擦除仅发生在注册等冷路径上，热路径只保留单态调用。

## 策略对比与选择

| 手段 | 消除的开销 | 成本 / 风险 | 适用场景 |
|------|-----------|-------------|---------|
| `final` | 内联损失 + 预测失败 | 几乎为零 | 类层级已定型 |
| LTO | 同上 | 构建复杂度上升 | 类层级跨编译单元定义 |
| PGO + ICP | 同上 | 构建流程两阶段化 | 调用点多态但偏科 |
| 模板 / CRTP | 全部（无 vptr） | 代码膨胀、类型不可统一存储 | 类型集编译期已知 |
| `std::variant` + `std::visit` | 全部 | 类型集必须封闭 | 类型集有限且较小 |
| 函数指针 + context | 预测失败、堆分配 | 类型安全由调用方保证 | 运行期动态注册、订阅回调 |

最后一条规范：**先测量，再优化**。虚调用的损失是"失去内联 + 预测失败"的组合，只有确认某个调用点真的是瓶颈（profiler 证实）才值得动手。多数程序中虚调用占比极小，去虚化收益不到 1%——此时 `final` 与 LTO 这类零成本手段足够，`std::variant` 重构反而引入不必要的代码复杂度。

---

> **小结**：虚调用的开销按量级排序为失去内联、分支预测失败、缓存、指令与 ABI、对象布局；消除手段按侵入性递增为 `final`、LTO、PGO + ICP、模板/`std::variant` 等设计替代。去虚化的前提是编译器能确定或推测具体类型，其边界始终是完整类型可见性与语义安全。
